# SMS delivery watch

Deploy the Nexus API, core API and frontend together. Apply
`app/db/migrations/2026_22_sms_monitoring.sql` once to the SentinelOps access
database (the identical copy in the core API is for the same database).
Assign **SMS queue monitoring** to the relevant sections in Section & Module
Access. Existing sections do not inherit access to customer messages.

## Nexus API configuration

Set these in the server environment or its existing private `.env`:

```dotenv
SMSAL_HOST=<notification database host>
SMSAL_PORT=5342
SMSAL_DATABASE=postgres
SMSAL_USERNAME=<read-only monitoring account>
SMSAL_PASSWORD=<password>
SMSAL_TIMEZONE=Africa/Harare
SMSAL_SSLMODE=prefer
```

Restart the Nexus API after configuration. Africa/Harare is the initial assumption
for the source's timestamp-without-time-zone clock; confirm with the source owner.
Use UTC instead if those columns contain UTC. Browser dates are converted from
this setting. Configure SSLMODE to match the database's supported TLS policy.
No credentials are sent to the browser.

The source account needs CONNECT on `postgres`, USAGE on `public`, and SELECT on
`public.queue` only. Use a dedicated account with no inherited write privileges.
Every monitoring transaction is additionally opened READ ONLY. This feature
does not send, retry, edit, delete, archive, or acknowledge SMS records.

## Evidence and load

- Only `channel='SMS'` and `deleted IS NOT TRUE` are observed; EMAIL is excluded.
- SEND is the source's status, not independently confirmed handset delivery.
- Counts describe currently retained records, not all-time totals. Archiving can
  reduce them. Updated SEND records are not a measured gateway throughput rate.
- Committed source changes invalidate overview snapshots immediately. Concurrent
  overview refreshes are coalesced with a bounded wait; a one-second cache covers
  simultaneous readers. Up to three source reads
  run concurrently per process. Each statement is limited to 8 seconds and
  connections to 5 seconds. Live subscriptions pause while the page is hidden.
- Records use 50-row keyset pages. Exact recipient/ID and source searches avoid
  searching message text. Recipients are masked in the list; authorized operators
  can view message evidence in the detail drawer. No export of customer messages
  is introduced.
- A refreshed older page stays on its ID boundary; return to page 1 for new IDs.
- One-hour backlog filtering is an investigative threshold, not an asserted SLA.

Before production, the source DBA should inspect query plans and existing
indexes. Useful partial indexes include `id DESC`, `(status,id DESC)`,
`(created_at)`, `(source,id DESC)`, and `(recipients)` with predicate
`channel='SMS' AND deleted IS NOT TRUE`. Do not create overlapping indexes
blindly: the queue is also a write-heavy operational source. Overview aggregation
still scans retained SMS entries and is bounded by the statement timeout.

## Welcome notifications

The core API schedules one welcome after successful user creation. It persists a
targeted inbox notification and sends email with the existing renderer and SMTP
transport, using the configured FRONTEND_URL. No password is included. Inbox and
email failures are isolated and logged; they cannot roll back the new account.
This uses the existing process background-task mechanism, not a durable email
outbox: a process termination before completion can interrupt delivery. Editing
an existing account does not send another welcome. No automatic historical-user
mailing is performed.

## Acceptance checks

With a test account, confirm the configured-host CTA, one inbox welcome, and one
email. In Reporting → SMS delivery watch, verify known source counts, source
timezone, read-only account privileges, source status evidence, filtering,
refresh/pause, and an archived record returning a clear not-found response.
Automated tests use synthetic data and mocked transport; no customer SMS or live
email is generated by those tests.

## Real-time source events (required for event-driven operation)

Run `deploy/sms_source_realtime.sql` **on the SMS source database**, as the owner
of `public.queue`. This is separate from the SentinelOps access migration above.
The migration installs AFTER triggers for changes and truncation, plus a small
notification function. It does not modify existing queue rows, statuses, retries,
or the sending service. Its two-second lock timeout makes installation fail rather
than wait indefinitely for the live queue. Review/install it through the source
database's normal deployment procedure.

The triggers emit a constant, customer-data-free PostgreSQL NOTIFY at commit.
Insert, update, delete, SMS-to-EMAIL transitions and archiving are covered;
EMAIL-only row changes are ignored. Rolled-back transactions emit no event.
Identical notifications inside a bulk transaction are coalesced by PostgreSQL.
The source gains the small trigger/NOTIFY overhead; monitor the database's
notification queue normally. The application monitoring account remains read-only.

One LISTEN connection per Nexus API process serves all viewers and closes when
no viewers remain. The browser subscribes using an authenticated fetch stream,
never a token in the URL. Events invalidate filtered records, overview evidence,
and an open message drawer. Reads are coalesced during bursts; rendering latency
still depends on source query execution and network latency. This is not a
historical event log: reconnects obtain a fresh snapshot to recover missed changes.

Without both enabled source triggers, the UI explicitly says **Polling fallback ·
1s**. After installation the listener detects the triggers within ten seconds and
switches to **Live · source events**. It uses a thirty-second clock refresh for
age-based metrics even when no records change; record-change events do not wait
for this refresh. No fifteen-second browser polling remains.

The stream renews every twenty seconds through ordinary authentication and
module authorization. Source disconnection or stalled heartbeats are visible;
client retries back off to at most five seconds. Browser invisibility, pause and
unmount close the subscription. Preserve `text/event-stream` responses through
your proxy, disable response buffering on `/api/v1/nexus/reports/sms/events`, and
allow streaming connections longer than twenty seconds. `X-Accel-Buffering: no`
is supplied by the API. Do not put this route behind a buffering response cache.

To verify after deployment, use an approved source-service test operation and
observe its committed change without pressing Refresh. Do not modify real customer
messages just to test monitoring. Confirm that pausing, reconnecting and losing
section access behave correctly. These source hooks have been prepared, not
automatically executed by the development agent.
